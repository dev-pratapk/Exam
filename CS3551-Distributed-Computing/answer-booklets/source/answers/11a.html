Introduction

Processes in a distributed system have no shared memory, so they cooperate by message passing. The two basic communication primitives are Send(destination, message) and Receive(source, &message). A message consists of a header (source, destination, type, length) and the data. The semantics of these two calls — whether the caller waits, and whether the message is stored on the way — decide the synchrony of the communication.

Buffered and unbuffered communication

  • Unbuffered (rendezvous): there is no temporary storage. The sender and the receiver must both be at the communication point at the same time; a Send cannot complete until the matching Receive is executed.
  • Buffered: the message is first copied into a buffer (sender-side kernel buffer, or a receiver mailbox/port) and the sender is released. The buffer decouples the two processes in time, but a finite buffer may still block the sender or force message loss.

“Synchronous” means the Send is tied to the matching Receive; “asynchronous” means the Send completes once the data has been copied out of the user buffer, without waiting for the Receive. “Blocking / non-blocking” describes whether the calling process waits for the call to return. These two ideas combine into four Send variants.

Thus a blocking synchronous Send is the tightest form (both processes meet); a non-blocking asynchronous Send is the loosest form (fully decoupled). The intermediate forms trade latency against buffer space and programming complexity.

Receive primitives

  • Blocking Receive: the process blocks until a message is available (from a buffer or directly from a sender) and then returns it. Simple, but the process is idle meanwhile.
  • Non-blocking Receive: the call returns immediately with a status; if no message is present it returns a null/empty value. The process must poll, which wastes CPU but keeps it responsive.

With an unbuffered channel, a blocking Receive must wait for a sender; with a buffered channel, it completes at once if the buffer is non-empty.

Handles and Wait()

A non-blocking Send (and non-blocking Receive) returns a handle — an identifier for the pending operation. The process continues with useful work and later calls Wait(handle) to block until that operation completes, or Test(handle) to check completion without blocking. This is how computation and communication are overlapped. MPI implements it with MPI_Request, MPI_Isend / MPI_Irecv, MPI_Wait and MPI_Test.

Processor synchrony

A system is synchronous if all processors advance in lock-step with a known bound on message delay; it is asynchronous if processors run at independent speeds with unbounded delay and no global clock. In a synchronous system a blocking Send/Receive pair is easy to reason about; in an asynchronous system, buffering and non-blocking primitives are used to hide latency and avoid deadlock. Note that “synchronous send” (sender–receiver coupling) is a different idea from “synchronous processor” (lock-step execution).

Conclusion

Send/Receive primitives differ in blocking (does the caller wait?) and synchronous (is the message buffered or must a rendezvous occur?). Blocking synchronous gives the strongest coupling, non-blocking asynchronous the weakest; handles with Wait() let a process overlap communication with computation. The right library or standard — sockets, MPI/PVM, RPC/RMI, CORBA/DCOM or MOM — is chosen from the required coupling, performance, heterogeneity and language support.
