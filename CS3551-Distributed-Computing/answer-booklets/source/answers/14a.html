Introduction

A checkpoint is a saved copy of the local state of a process on stable storage. In checkpoint-based rollback recovery, after a failure the processes roll back to a set of checkpoints and restart from there. The set must form a consistent global state, called a recovery line: it must contain no orphan message, that is, a message whose receive is recorded but whose send is not.

1. Checkpoint-based recovery approaches

ApproachHow checkpoints are takenAdvantageDisadvantage
Uncoordinated (independent) checkpointingEach process takes checkpoints on its own, without coordination. The dependencies between checkpoints are recorded and a recovery line is searched for after a failure.Simple; no run-time coordination; each process picks convenient times.Domino effect (rollback may go back to the initial state); useless checkpoints; garbage collection is needed; several checkpoints per process must be kept.
Coordinated checkpointingThe processes coordinate and take checkpoints together so that the set is consistent. It may be blocking (processes stop sending messages during the protocol) or non-blocking (for example Chandy–Lamport markers).Always a consistent set; no domino effect; only the last checkpoint is needed; simple recovery.Coordination messages and delay; blocking reduces performance; one initiator is a possible bottleneck.
Communication-induced checkpointingProcesses take local (basic) checkpoints independently and are forced to take additional checkpoints, driven by information piggybacked on application messages. It is model-based or index-based.No domino effect; no separate coordination messages; processes are autonomous.Extra forced checkpoints, which can be many; piggybacked data increases message size.

2. Coordinated checkpointing: the Koo–Toueg algorithm

Koo and Toueg’s algorithm is a blocking coordinated algorithm that checkpoints only the processes that must be checkpointed (a minimal set).

Assumptions: channels are FIFO and end-to-end protocols (such as sliding window) are used; communication failures do not partition the network; one process initiates the checkpointing; no failure occurs during the protocol.

First phase (tentative checkpoints)

  1. The initiator Pi takes a tentative checkpoint and sends a request to every process from which it received a message since its last checkpoint. The request carries the label of the last message Pi received from that process.
  2. A process Pj that receives the request takes a tentative checkpoint if it has sent Pi a message after its own last checkpoint, because otherwise that message would become an orphan. Pj then sends requests in the same way to the processes it has received messages from.
  3. A process that does not need a new checkpoint, or has already taken one for this initiation, replies yes. After taking a tentative checkpoint, a process does not send application messages until the second phase ends (this is why the algorithm is blocking).
  4. Pj sends yes to its requester when all the processes it asked have answered yes; if any process answers no, it answers no.

Second phase (decision)

  1. If the initiator receives yes from all the processes it asked, it decides that all tentative checkpoints become permanent; otherwise it decides to discard them.
  2. The decision is sent to all processes that took tentative checkpoints. Each one makes the checkpoint permanent (and deletes the older one) or discards it, and then resumes sending messages.

Illustration

P1 received m1 from P2, and P2 received m2 from P3, after their last checkpoints. P1 starts the algorithm.

StepWhat happens
1P1 takes a tentative checkpoint and sends a request to P2, because P1 received m1 from P2 after its last checkpoint. P1 stops sending application messages.
2P2 had sent m1 after its last checkpoint, so it takes a tentative checkpoint. It sends a request to P3, because P2 received m2 from P3.
3P3 takes a tentative checkpoint. It has received no message from any other process since its last checkpoint, so it replies yes to P2.
4P2 replies yes to P1.
5P1 has all the yes replies, so it sends commit to P2 and P3. All three tentative checkpoints become permanent and the processes resume sending messages.

Recovery in the Koo–Toueg algorithm

It also has two phases. In the first, the initiator asks the processes that must roll back whether they are willing; a process must roll back if it has received a message from the initiator that the initiator’s checkpoint does not show as sent (otherwise that message would be an orphan). In the second phase, if all agree, the initiator tells them to roll back to their last permanent checkpoint and restart; otherwise recovery is aborted.

Correctness

The permanent checkpoints are consistent because every process that sent a message received by an already-checkpointed process also takes a checkpoint, and application messages are not sent between the tentative checkpoint and the decision, so no orphan message can be created. Only processes that communicated since the last checkpoint take part, so the set is minimal. There is no domino effect, and only one permanent checkpoint per process has to be kept.

Hence checkpoint-based recovery is uncoordinated, coordinated or communication-induced, and the Koo–Toueg coordinated algorithm takes a minimal consistent set of checkpoints in two phases (tentative, then permanent).
